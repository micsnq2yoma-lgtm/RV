# 导航 Demo：RV 板上的智能体控制移动机器人到达目标位置

- **作者**：Claude（维护者要求直接实现，不经任务单）
- **日期**：2026-11-15
- **性质**：仅仿真。电脑跑 MuJoCo 物理和渲染；感知、路径规划、里程计、行驶控制和 DeepSeek 智能体都在 RV 板上。

## 1. 演示内容

场地约 4 m × 3 m，四周有墙，场内有 3 个固定箱子。地面上有红、绿、蓝、黄四个目标区，另有灰色的起点区。一台 40 × 30 cm 的差速轮式小车从起点出发，用户用中文下达指令，例如：

| 场景 | 指令 | 真值判定（运行结束后由面板读取 `truth`） |
|---|---|---|
| N1 | 去蓝色区域 | 小车中心在蓝区内 |
| N2 | 先去绿色区域，再去蓝色区域，最后回到起点 | 依次经过绿区、蓝区、起点（按子序列匹配），且最后停在起点区内 |
| N3 | 去红色区域，路上不要经过黄色区域 | 小车中心在红区内，并且全程没有进入过黄区 |
| N4 | 去红色区域 | 小车中心在红区内。小车出发后，仿真端会在主通道 (0.2, 0.25) 落下一个箱子（板子事先不知道） |

## 2. 分工与数据流

```
浏览器（电脑）
  ├─ 视角画面 ← http://127.0.0.1:8091/stream/{chase|top|front|side}.mjpg ← nav_server.py（电脑）
  └─ 页面、事件、主板数据 ← http://192.168.50.2:8080 ← nav_dashboard.py（RV 板）

nav_server.py（电脑） ──TCP 15003，电脑主动连板子，不改防火墙──▶ RV 板
   hello / render / drive / odom / reset / truth（truth 只给评估用）
```

| 层 | 位置 | 做什么 |
|---|---|---|
| 智能体 `nav_agent.py` | 板 | DeepSeek `deepseek-flash`，开 thinking，`tool_choice=auto`。工具：`update_plan`（不算动作）、`navigate_to(target, avoid)`、`finish`。每轮只发文字：小车位姿、所在区域、已到过的区域、上一步结果。原话逐字推给工作台 |
| 感知 `nav_perception.py` | 板 | 俯视相机 640×480。车身上前青、后品红两个色标，算出位置和朝向；四个目标区靠颜色分割，并记住看得最完整的那一次；障碍物只取被照亮的顶面（棕色箱子，或低饱和度、亮度 < 190 的墙），按 0.35 m 高度投影到 5 cm 栅格，做一次开运算去掉细线。小车附近的格子沿用上次看到的状态 |
| 规划 `navigator.plan` | 板 | 障碍膨胀 0.29 m（车身半对角线 0.26 m 加 0.03 m 余量），`avoid` 区域额外膨胀车身半径；8 邻域 A*，再做视线捷径平滑 |
| 行驶 `navigator.Driver` | 板 | 用编码器角度积分里程计；纯追踪，前视 0.35 m，最高 0.3 m/s，20 Hz 下发轮速。每走 0.7 m 或每 2.5 s 停车，用俯视图重新定位一次，并检查有没有**新出现的**障碍挡住剩余路线（只看规划时没有、成团至少 4 格的占用）。编码器显示走了 ≥ 10 cm、相机显示不到 3 cm 时，判定为卡住。起步时离障碍不到 0.27 m 的话，先直行 0.25 m 再转向 |
| 仿真 `nav_server.py` | 电脑 | 物理 500 Hz 实时步进；0.5 s 收不到 `drive` 就停车；渲染线程同时处理板子请求和 MJPEG 推流 |

## 3. 运行

板子侧（Ubuntu chroot，`/tmp` 绑定到 Buildroot 的 RAM）：`sh /tmp/rv014/run_nav.sh`。电脑侧：

```powershell
.venv/010/py/Scripts/python.exe sim_agent/pc/nav_server.py --mjpeg 127.0.0.1:8091 --seconds 14400
python sim_agent/pc/archive_dashboard.py --out <归档目录> --manifest --files-every 2
```

浏览器打开 `http://192.168.50.2:8080`，选场景 N1–N4（会自动填入指令），或者输入自由指令，再点“开始任务”。录像用 `sim_agent/pc/record_page.py`：它用无头 Chrome 只录工作台这一个页面，不录桌面。

离线测试（电脑，不需要板子和 API Key）：`python -m unittest test_nav`。测试用真实物理、渲染和板上感知、规划、行驶代码，模型换成按剧本出牌的假模型，覆盖 N3 避让、N4 被挡后重新规划、拒绝违规调用三个用例。

## 4. 开发中发现并修正的问题

| 现象 | 原因 | 修正 |
|---|---|---|
| 仿真发散 | 轮子转动惯量太小，速度执行器增益过大 | 轮关节加 armature，用 implicitfast 积分器 |
| 轮子空转，车速只有理论值的 1/3 | 万向球和驱动轮一样高，分走了车重 | 万向球抬高 3 mm |
| 3 m 路程 2 秒走完 | 物理循环每批只睡 2 ms，节拍追不回来 | 按整批的应有时刻睡足 |
| 墙角的红区、绿区规划不出路径 | 墙的侧面像素按顶面高度投影，被推向场内 | 只用被照亮的顶面 |
| 途中误报“路被挡住” | 不同位置拍到的栅格边缘有几格起伏 | 只把新出现、成团的占用算作新障碍 |
| 车顶上突然出现的箱子，被卡死 | 箱子放在车前 1 m，和固定箱子之间只剩一条缝 | 改为在主通道上的固定位置落下 |
| 板上误报“卡住” | 板上一次定位要 1–2 s，按开始时刻计时，两次定位之间几乎没走 | 计时从定位完成算起；卡住要求编码器和相机的位移对不上 |
| 回起点时规划失败 | 起点灰色垫块的边角亮度 < 205，被当成障碍 | 障碍改用颜色判断，不再只看亮度 |
| 场地中央落下的箱子漏检 | 中央光照强，箱顶亮度 212 | 同上 |
| 小车钻进箱子和 box1 之间的窄缝 | 抹掉车身周围像素时，把旁边箱角也抹掉了 | 抹除半径缩小，被遮住的格子沿用记忆；起步时净空不足就先直行再转向 |

已知的不足：

- 模型的思考开头常常是英文，后面才转成中文；
- 板子做一次俯视定位要 1–2 秒，行驶会“停—看—走”；
- 整板偶发失联（DECISIONS 中“暂缓排查”的问题）在导航演示里也出现了 1 次。
