## 需要回答的问题

### 1. 中断线程、RT throttling与检测功能

| 线程/IRQ | 策略/优先级 | 线程允许CPU | IRQ有效CPU |
|---|---|---|---|
| 串口IRQ12，f9c250000.serial | FIFO50 | 0 | 0 |
| eth0 IRQ13 | FIFO50 | 0 | 0 |
| eMMC IRQ16，f9cda1000.mmc | FIFO50 | 0 | 0 |
| TF IRQ15，f99f04000.mmc | FIFO50 | 0 | 0 |

IRQ配置mask显示0–1，而有效affinity和中断线程允许CPU为0。控制主线程绑定CPU1，Python负载绑定CPU0；故不能仅凭80>50便断定控制线程直接饿死同核中断。RT runtime=950000µs、period=1000000µs，未改变。只有两颗物理核，启动中CPU2–7失败沿用已知设备树配置问题。

`/proc/sys/kernel/sysrq`、`/proc/sysrq-trigger`、`/proc/config.gz`不存在；未找到watchdog、softlockup_panic、hung_task_timeout_secs，panic=0。未取得构建配置，无法最终确认对应检测功能是否编入。没有发现可读的thermal_zone温度值。[Linux SysRq文档](https://docs.kernel.org/admin-guide/sysrq.html)要求内核及串口支持，因此本次“无响应”有取证能力限制。

### 3. 失联、SysRq和恢复信息

原E4于本地01:09:14正常卸载Ubuntu。下一个准备命令重新挂载、绑定RAM/tmp并调用make/ldd，串口最后确认01:09:39挂载，之后SSH读取超时。该命令链没有运行rt_ctl；由于最初编译工具缓冲stdout直到结束，超时丢失了部分输出，无法定位最后执行的子命令，不能直接归因于gcc。后续工具改为即时保存阶段标记，复位后同样的编译正常完成。

主机网口仍Up/100Mbps、固定IP未变，ping连续失败、ARP为Incomplete。01:11:14开始追加观察30秒，01:11:44/49/54发送BREAK+w/l/t，没有内核诊断输出；普通串口存活标记和uptime随后等待10秒也收到0字节。人确认主电灯亮、无明显发热、接线未变，再按RESET。恢复挂载出现EXT4 journal recovery；dpkg --audit为空，numpy1.26.4可用。没有取得oops、RCU stall或其他异常栈。

这次是实验窗口外的整板失联，不能改写各窗口内结果；也证明本轮现象不只发生在运行FIFO80控制器时。仍无法在内核/驱动、硬件/供电/温度、CPU与I/O交互之间定因。主观无明显发热不等于温度或供电已被仪器排除。

### 4. 仿真端十分钟指标

完整配置指标见上表。正式计数窗口满足阈值的有：E4-verified, E5。PC看门狗计数贯穿整个窗口；C的lifetime计数跨reset保留，避免只读取最后一个短周期。PC的sent/received/RTT和普通C统计按协议在reset后归零，不能把最后一行这些字段解释成整个十分钟的总计；不将打印周期中的零丢包冒充跨reset全窗口零丢包。

E1的看门狗虽然被程序标成board_silence，同期PC有97.5967ms物理步间隙、99.5803ms发送间隙；当前分类以单步间隙≥98ms判断，不能据此断言板子是原因。原E4同期PC发送间隙82.5039ms，对应板端观测83.010643ms。保留所有失败窗口，不把多个短窗口拼成十分钟，也不把一次达标等同长期稳定。

### 5. 后续配置和建议

继续用CPU1运行控制器、CPU0运行Python；源码/二进制放Buildroot/tmp，需chroot时将同一RAM目录绑定进去。运行日志与图片写RAM并同步流式取回电脑，正常结束后再取完整文件；避免把eMMC输出写入和实时试验混为一个变量。

本轮不足以证明“只有FIFO80会失联”，因此保留默认FIFO80，不改设计文档的默认策略；新增FIFO40和SCHED_OTHER作为可重复的诊断选项。维护者可根据表内达标样本选择下一轮配置，但目前没有已证实的根因修复方案。建议维护者提供启用SysRq/lockup取证且确认串口支持的诊断镜像，审阅无控制器运行时的准备阶段失联，再安排CPU/I/O交互或硬件层定位。本任务没有自行修改内核或推进S4。
