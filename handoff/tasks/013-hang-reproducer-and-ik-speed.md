# 任务 013：找一个能快速复现失联的负载 + IK 提速

- **对应阶段**：S3 收尾
- **作者**：Claude
- **日期**：2026-11-08
- **电机是否可能动作**：**否**
- **前置条件**：分支 `task-013-repro-ik`，基于 `task-012-hang-isolation`，再合并上游 `handoff-protocol`。必须先读 `docs/STABILITY.md`（任务 012 的取证方法）。

## 背景（报告 012 的结论）

- E1–E6 六组实验各跑 10 分钟，**全都没有失联**：CPU 满负载、eMMC 持续写入 4.35 GiB、FIFO80/40/OTHER 三种优先级都试过。
- 第三次失联发生在**实验之外**：刚卸载 Ubuntu，紧接着重新挂载、bind `/tmp`，运行 `make`（调用 gcc）和 `ldd`，**大约 25 秒后**整板没了响应。当时 `rt_ctl` **没有在运行**。
- 内核没有 SysRq，没有 softlockup/hung task 检测，`panic=0`，所以失联时没有任何内核输出。
- 三次失联都发生在 **eMMC Ubuntu 处于活动状态**的时候：011 的两次是技能循环正在运行（Python 不断读取 numpy 库），012 的一次是挂载后编译。E3 那种大块**顺序写**没有触发；**大量随机小文件读取**（gcc、ldd、Python import）还没有单独测过。另外，**卸载后马上重新挂载**这个动作也还没测过。
- 串口一个字节都不回、SysRq 也没反应，这种“完全静默”的卡死，更像是**硬件层面**的问题：总线锁死、内存或供电问题，而不是一般的软件死锁。

## 目标

1. 找到一个能在 **20 分钟内**稳定触发失联的负载。有了它，就能把问题交给维护者去查；我们自己也能有针对性地绕开。
2. 把 IK 从约 1.6 s 一次降到 **≤ 50 ms**。这是 S4 的前置条件，和失联问题无关。

## 不要做的事

- 不改内核、设备树和固件。不动 eth1，不改电脑的 Clash 和防火墙。
- 日志写到 `/tmp`（内存里），并通过 SSH 实时取回电脑；串口全程录制。
- 失联时按 `docs/STABILITY.md` 的流程取证后，再请人按 RESET。

## 步骤

### A. 现场信息（每次开机都要确认）

1. **[需人工]** 请人确认**板子现在怎么供电**：是 DC 电源插座（DC1），还是 **USB-C 调试口（USBC1）**？SW6 开关拨在哪个位置？如果用的是 DC 电源，电源适配器的规格是多少（电压和电流）？原理图上 SW6 用来选择 DC 输入还是 USB-C 的 VBUS。如果板子是靠电脑 USB 口供电，负载一高就可能电压不足，**这本身就可能是失联的原因**。
2. 如果板子现在是 USB-C 供电，并且手边有 DC 电源：**[需人工]** 请人在 B 节开始前改成 DC 供电，并在报告里注明。

### B. 复现负载实验

每组实验最多跑 20 分钟，跑到失联为止。电脑全程 `ping -t 192.168.50.2`，串口全程录制。实验顺序如下，**一旦复现，先取证，再进入 C 节**：

| 编号 | 负载 | 要验证什么 |
|---|---|---|
| R1 | 循环 100 次：以读写方式挂载 `mmcblk1p1` → bind `/tmp` → 在 chroot 里执行 `ldd /usr/bin/python3` 和 `python3 -c "import numpy"` → 卸载。两次循环之间不等待 | 卸载后马上重新挂载，以及大量随机读 |
| R2 | 挂载后，在 chroot 里循环执行 `make clean && make`（编译 `rt_ctl`），每次编译前先 `echo 3 > /proc/sys/vm/drop_caches` | 重现 012 失联时的现场 |
| R3 | 挂载后，循环执行 `echo 3 > /proc/sys/vm/drop_caches; tar -cf - /mnt/ubuntu/usr \| cat > /dev/null`。这条命令在 Buildroot 里运行，不进 chroot | eMMC 大量随机小文件读取，不涉及编译 |
| R4 | 同 R3，但读的是 TF 卡：`tar -cf - /media \| cat > /dev/null`，TF 卡以只读方式挂载 | 换成另一个 MMC 控制器，看是不是 eMMC 特有的问题 |
| R5 | 内存压力测试：在 chroot 里通过代理隧道安装 `memtester`（也可以装 `stress-ng`），然后执行 `memtester 768M 3`（绑定 CPU0）。另开一个进程在 CPU1 上也跑 `memtester 512M 3` | DDR 和内存稳定性 |
| R6 | R3 和 R5 同时运行 | 内存和 I/O 一起加压 |

R5、R6 安装软件时需要打开代理隧道（参照任务 008）。**装完就关掉隧道**，再开始计时。

每组实验结束后，如果没有失联，记录：`/proc/interrupts` 的增量、`dmesg | tail -30`、读取的数据量和循环次数。

### C. 一旦复现

3. 同一个负载**再跑 2 次**，记录每次从开始到失联的时间。
4. 尝试缩小范围，例如：
   - R1 改成只读挂载、不 bind；
   - R3 的读取量减半；
   - 只用一个 CPU（用 `taskset` 或 Python 设置 affinity，把整个负载限制在 CPU0）。

   每个变体跑 1–2 次。
5. 把**最小复现步骤**写进 `docs/STABILITY.md`，写成维护者拿到就能照着做的形式。

### D. IK 提速（和 B、C 互不影响，可以穿插进行）

6. 用 `cProfile` 分析当前 `kin.py` 的 `ik()`，找出最耗时的部分。在报告里给出前 10 个最耗时的函数。
7. 优化方向，按顺序尝试，达标就停：
   - a. 热启动：用当前关节角，或者上一次的解作为初值；
   - b. 正运动学和雅可比**一次算出来**，避免重复计算；把逐元素的 Python 循环改成 numpy 向量运算，或者直接用纯 Python 的 3×3 矩阵运算（矩阵很小的时候，numpy 调用本身的开销反而更大）；
   - c. 调整阻尼系数和步长，减少迭代次数；
   - d. 还不够的话，把 FK、雅可比和 DLS 改用 C 实现（编译成 `.so`，Python 用 `ctypes` 调用），精度要求不变。
8. 用任务 011 的方法重新验收：30 个目标点全部收敛，位置误差 < 1 mm，姿态误差 < 1°；记录板子上的平均耗时和最大耗时。目标：平均 ≤ 50 ms。
9. 用新的 IK 重跑 011 的任务 2（叠放）5 次。要求 5/5 成功，并记录每次试验的耗时，和 011 对比。

### E. 整理

10. 更新 `docs/STABILITY.md`。写报告 `handoff/reports/013-hang-reproducer-and-ik-speed.md`，更新 `STATUS.md`，发 PR。
